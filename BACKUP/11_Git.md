# git 提交分类的判断清单

这里为你整理了一份‌覆盖所有主流Git提交分类的全场景判断清单‌，结合业务开发场景明确每个类型的适用边界、典型场景和避坑要点，你可以直接对照业务改动快速判断分类：

## 1. 全类型核心判断清单

| 提交类型     | 核心判定标准                       | 典型业务场景                                               | 绝对不能选的场景                   | 规范示例                               |
| ------------ | ---------------------------------- | ---------------------------------------------------------- | ---------------------------------- | -------------------------------------- |
| `feat`     | 新增用户/业务可见的完整功能、模块  | 新增用户注册/支付模块、新增导出报表功能、新增页面路由      | 仅修改内部逻辑、修复Bug、调整样式  | feat(order): 新增订单批量导出功能      |
| `fix`      | 修复已存在的Bug、错误行为          | 修复登录空指针异常、修复支付金额计算错误、修复页面白屏问题 | 新增功能、纯格式调整、性能优化     | fix(pay): 修复支付金额精度丢失问题     |
| `perf`     | 仅提升系统性能，不改变功能逻辑     | 优化数据库查询速度、减少页面重绘、接口响应耗时优化         | 修复Bug、新增功能、普通重构        | perf(list): 优化商品列表懒加载渲染性能 |
| `style`    | 仅调整代码格式，完全不涉及逻辑改动 | 统一缩进为2空格、移除多余空行、用Prettier格式化代码        | 修改CSS样式、调整业务逻辑、修复Bug | style: 全量格式化代码统一缩进规范      |
| `refactor` | 重构代码，既不加功能也不修Bug      | 提取公共工具函数、简化嵌套分支、重命名语义化变量           | 新增功能、修复Bug、性能优化        | refactor(user): 抽离用户校验公共逻辑   |
| `docs`     | 仅修改文档、注释类内容             | 更新README部署文档、补充API接口注释、修正CHANGELOG         | 修改业务代码、调整配置文件         | docs: 更新项目Docker部署指南           |
| `test`     | 仅修改测试相关代码                 | 新增登录接口单元测试、补充异常场景Mock用例                 | 修改业务代码、调整生产配置         | test(login): 新增登录失败场景测试用例  |
| `chore`    | 构建/依赖/工具类辅助改动           | 升级Vue版本、更新ESLint配置、调整CI流水线                  | 修改业务功能、新增页面逻辑         | chore: 升级React到18.3正式版本         |
| `revert`   | 完全撤销之前的某次提交             | 回滚未上线的错误提交、撤销有问题的feat功能                 | 手动修改代码覆盖旧逻辑             | revert: 撤销"feat: 新增临时活动页"提交 |

## 2. 业务场景快速判断流程图

1. 改动是新增用户可见的功能 → 选 ‌`feat`‌
2. 改动是修复线上/测试发现的错误 → 选 ‌`fix`‌
3. 改动仅提升运行速度/资源占用 → 选 ‌`perf`‌
4. 改动完全不碰代码逻辑，只调格式 → 选 ‌`style`‌
5. 改动优化代码结构，不加功能不修Bug → 选 ‌`refactor`‌
6. 改动只涉及文档、注释、说明类内容 → 选 ‌`docs`‌
7. 改动只针对单元测试/集成测试代码 → 选 ‌`test`‌
8. 改动是依赖升级、配置调整、工具链更新 → 选 ‌`chore`‌
9. 改动是用Git命令直接回滚历史提交 → 选 ‌`revert`‌

## 3. 高频易混淆场景判定指南

- 调整页面UI布局：如果是修复样式错位 → fix；如果是全新改版新增交互 → feat；如果仅调整CSS缩进格式 → style
- 升级第三方依赖：如果是修复依赖漏洞 → fix；如果是常规版本迭代 → chore
- 优化接口响应速度：如果是修复慢查询Bug → fix；如果是在正常逻辑基础上做性能提升 → perf

# 下上班git操作

## ✅ 假设只关心的两个分支

| 分支            | 角色                            |
| --------------- | ------------------------------- |
| `product`     | 公共主分支（管理员维护）        |
| `dev`        | ✅ 你的开发分支（最终代码在这） |

---

## 🕔 每天下班前（固定 4 步）

> 目的：**保存当天工作 + 方便第二天继续**

```powershell
# 1. 确保在 dev
git checkout dev

# 2. 提交本地修改
git add .
git commit -m "feat: 当天完成的功能说明"

# 3. 拉取远端 dev（防止多端冲突）
git pull origin dev

# 4. 推送到远端
git push origin dev
```

✅ 到这里就可以安心下班了

---

## 🌅 第二天上班第一件事（固定 3 步）

> 目的：**拿到别人更新 + 对齐 product**

```powershell
# 1. 拿远端最新信息
git fetch origin

# 2. 切到 dev
git checkout dev

# 3. 把 product 的最新更新接进来（推荐）
git merge origin/product
```

如果有冲突：

```powershell
# 解决冲突后
git add .
git commit
```

最后：

```powershell
git push origin dev
```

---

## ✅ 每周 / 合并前必做（一次）

当你准备让管理员合并时：

```powershell
git fetch origin
git checkout dev
git merge origin/product
git push origin dev --force-with-lease
```


---

## 🚫 永远不要做的事

| 操作                         | 原因           |
| ---------------------------- | -------------- |
| 在 product 上开发        | 会被管理员打回 |
| 删除 product             | 公共分支       |
| 随意 `--force` product | 灾难           |
| 一天不 push dev             | 风险集中       |

---

## 🧠 记忆口诀（很重要）

> **上班中：commit + push dev**

> **上班前：fetch + merge product**
